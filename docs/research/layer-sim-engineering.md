# Engineering a growing layered tile sim (data-driven, debuggable, fast to iterate)

Researched 2026-10-27. Scope: how devs keep many layers, species and interactions manageable. Items marked **[unverified]** come from my general knowledge or secondary sources; items marked **[not found]** are things I searched for and could not confirm.

## Summary

- Every long-lived systemic game splits **content as data** (defs/raws/prototypes) from **a small set of code behaviours**. RimWorld (XML Defs + C# comps), Factorio (Lua prototype tables), Caves of Qud (blueprints + Parts + events), Dwarf Fortress (raws), Paradox (script files) all do this.
- N×M interaction explosion is avoided by **indirection**: entities declare tags/properties/channels, and rules act on those, not on named pairs (Zelda BotW "chemistry engine", Qud events, Unreal GameplayEffects).
- For grid data, the practical choice is **plain typed arrays per layer** (SoA), a fixed system order and per-system periods. Noita-style chunks/dirty rects only pay off at pixel scale, and GPU only at large grids (a 100×100-ish grid is far below that).
- Explainability is cheapest when **every computed value can return its breakdown** (RimWorld stat parts, Paradox `GetScriptValueBreakdown`), plus overlays and a cause-tagged event log.
- For emergent sims, the indie-realistic testing set is: a headless runner, a few fixed seeds, invariant checks, 4-6 ecological metrics, a parameter sweep script, and a state-hash golden test. Tarn Adams' and ONI's internals are poorly documented, so there is little "proof" of what indies do; treat this as design advice.
- JS determinism: `+ - * /` and `sqrt` are IEEE-exact; `Math.sin/exp/pow` etc. are implementation-dependent; `Math.random` is unseedable. Use a seeded PRNG and avoid or tabulate transcendentals.
- Tynan Sylvester's warning: players cannot read a deep ecosystem; keep the sim simple enough to "observe and comprehend". This matters for 100+ species.

## 1. Data-driven rules and effects

- **RimWorld**: content lives in XML `Def` files; each Def type maps to a C# class. A `ThingDef` is a template, and behaviour is attached through `comps` (a `CompProperties` entry creates a `ThingComp` instance); static-only data can use `DefModExtension`. Mods alter Defs via XML patches (since A17) instead of editing core files. Source: [RimWorld Wiki, ThingComp](https://www.rimworldwiki.com/wiki/Modding_Tutorials/ThingComp), [RimWorld Wiki, XML Defs](https://rimworldwiki.com/wiki/Modding_Tutorials/XML_Defs), [mod guide](https://github.com/roxxploxx/RimWorldModGuide/wiki/SHORTTUTORIAL%3A-Things-and-ThingDef-and-Components). Community docs, not Ludeon-official.
- **RimWorld stats**: a stat is `base value`, then offsets, then factors, with each source a `StatPart`; this makes any value decomposable. Source: [RimWorld Wiki, Stat](https://rimworldwiki.com/wiki/Stat) (order from `GetValueUnfinalized`). The tooltip code (`GetExplanationUnfinalized`) was **[not found]** in docs.
- **Factorio**: all content is `data.raw[type][name]` tables built in three rounds (`data.lua`, `data-updates.lua`, `data-final-fixes.lua`) across mods, then the Lua state is discarded. Unknown properties are ignored; missing required ones get defaults or an error. Source: [Factorio Data Lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html). Lesson for Clade: a "build phase" that validates and freezes data once at startup.
- **Caves of Qud**: an object is "a set of properties composed together", not a class tree (Bucklew). Mechanics run on **events**: Parts register for named events, a `FireEvent` goes to every part on the object, and a handler returning false stops propagation; `CascadeLevel` forwards events to inventory/equipment. Mods merge into blueprints with `Load="Merge"`. Sources: [Unity article](https://unity.com/en/resources/systems-driven-design-in-caves-of-qud), [Qud wiki, Events](https://wiki.cavesofqud.com/wiki/Modding:Events), [mod override note](https://wiki.cavesofqud.com/wiki/Modding:Parts). The IRDC 2015 talk "Data-Driven Engines of Qud and Sproggiwood" exists ([press kit](https://cavesofqud.com/press-kit/)); slides/video **[not found]**. Bucklew credits Scott Bilas' GDC 2002 data-driven object system ([RPG Site interview](https://www.rpgsite.net/interview/20000-brian-bucklew-caves-of-qud-interview-expansions-switch-port-unity-controller-support-coffee)).
- **Dwarf Fortress raws**: plain-text token files, one `[OBJECT:TYPE]` per file, materials as separate definitions, `REACTION`s as editable recipes (some hardcoded). Source: [DF wiki, Raws](https://dwarffortresswiki.org/index.php/v0.34:Raws), [Reaction](https://dwarffortresswiki.org/index.php/DF2014:Reaction). Pages are for old versions; wiki warns duplicate raws cause hard-to-diagnose problems.
- **Paradox**: modifiers in `common/modifiers` with an opt-in `stacking` flag (forum answer, unofficial: [Paradox forum Q&A](https://forum.paradoxplaza.com/forum/threads/modding-quick-questions-and-answers.1414681/page-93)); script values, scripted effects/triggers in separate folders; `script_docs` dumps every trigger/effect. Source: [CK3 Dev Diary 87](https://www.paradoxinteractive.com/games/crusader-kings-iii/news/dev-diary-87-royal-modding). I did not get an authoritative page on scripted-effect semantics.
- **Oxygen Not Included**: element table in game files; a fan DB (oni-db.com) maps relations between elements, buildings, critters, plants ([Klei forum](https://forums.kleientertainment.com/forums/topic/101019-tool-oni-database-quick-reference-guide-relations/), [wiki](https://oxygennotincluded.wiki.gg/wiki/Elements)). Klei devlog or talk on the gas/liquid sim: **[not found]** (only player speculation about cellular automata).
- **BotW "chemistry engine"** (GDC 2017, via secondary coverage): a small rule set over *elements* (fire, ice, wind) acting on material states, so objects respond to each other without pair-wise scripting; Fujibayashi called it "multiplicative" vs "additive" design. Sources: [GamesBeat](https://gamesbeat.com/the-legend-of-zelda-breath-of-the-wild-makes-chemistry-just-as-important-as-physics/), [Thumbsticks GDC recap](https://www.thumbsticks.com/gdc-17-breath-of-the-wild-science-lies). Secondary only.
- **Scribblenauts**: designers enter per-object properties (weight, flammability, element responses) in a tool; behaviour emerges from the property hierarchy ([GoNintendo coverage](https://gonintendo.com/?p=65324), secondary).
- **Unreal Gameplay Effects**: data assets with explicit stacking policy (clear stack on overflow, deny overflow, refresh duration, tick reset) and tag requirements. Source: [UE docs](https://docs.unrealengine.com/4.26/API/Plugins/GameplayAbilities/UGameplayEffect/index.html) (4.26 API; names may differ in UE5).

### Patterns that avoid N×M (synthesis, mostly **[unverified]** as a named doctrine)

1. **Tags/properties as the interface**: A rule says "things with `palatable` are eaten by things with `browser`", instead of "species 17 eats species 42".
2. **Channels / shared quantities**: species do not talk to species; they write to and read from layers (nitrogen, shade, humidity). Coupling count becomes species × layers, not species × species. This is what Clade already has.
3. **A fixed, small vocabulary of effect kinds** (e.g. `add_to_layer`, `scale_rate_by_layer`, `require_layer_range`, `spawn_on`), each implemented once in code; species data composes them. Same role as RimWorld comps / Qud parts.
4. **Explicit stacking and clamping rules** per channel (additive, multiplicative, max, saturating curve), declared once per layer, not per species. Paradox and Unreal both make stacking an explicit flag/policy.
5. **Pair tables only for exceptions** (a sparse override map), never as the default.
6. **Order of modifier application is fixed** (RimWorld: offsets then factors), so results do not depend on declaration order.

## 2. Grid architecture

- **Typed arrays per layer (SoA)**: bitECS docs recommend SoA typed arrays for locality, and note JS does not throw on out-of-range indices ([bitECS docs](https://cdn.jsdelivr.net/npm/bitecs@0.4.0/docs/Intro.md)). One author's benchmark claims large SoA speedups over OOP ([blog](https://ankursethi.com/blog/data-locality-sometimes-beats-algorithmic-complexity/)); single-source, indicative only.
- **ECS vs arrays**: ECS fits sparse, heterogeneous entities (animals, items). Grid layers are dense and uniform, so a flat `Float32Array(w*h)` per layer is simpler and faster. No source found arguing this explicitly (**[not found]**); this is my reasoning. If Clade has per-tile plant occupancy, `Uint16Array speciesId` + `Uint8Array age/size` is already "SoA ECS" without a library.
- **Memory-bound, not compute-bound**: Factorio's UPS on big bases is limited by memory latency; software prefetching gave 9-13% and shrinking per-animation data ~2% ([FFF-204](https://factorio.com/blog/post/fff-204)). Takeaway: compact, contiguous data beats clever algorithms; relevant only at scale far above Clade's likely grid.
- **Noita**: world in 64×64 chunks, each with a dirty rect; bottom-up update order; multithreading by a checkerboard over four rounds so threads never touch the same pixels. Source: [80.lv interview](https://80.lv/articles/noita-a-game-based-on-falling-sand-simulation/) (GDC 2019 talk itself not retrieved). Pixel-scale techniques; for tile grids of ~10^4-10^5 cells a full pass per tick is cheap, so dirty rects are optional.
- **Double buffering**: needed only where a cell's update reads neighbours that are also updated this tick (diffusion of humidity/nitrogen/shade spreading). Per-cell-local updates can be in place. **[unverified]**, standard CA practice.
- **Update scheduling**: slow layers (soil, nitrogen) every N ticks, fast ones (moisture) more often; order the systems explicitly in one list, with the dependency documented (e.g. shade → humidity → moisture → growth). Offset the phases of slow systems so one tick does not spike. **[unverified]**, general practice.
- **GPU/WebGL CA**: I found no benchmark for ~256² grids in JS (**[not found]**). Sources say GPU wins on large grids or many steps/frame, are limited by memory bandwidth, and are harder to maintain; one WebGL CA library itself recommends its CPU module for being more battle-tested ([cellular-automata-gpu README](https://github.com/kchapelier/cellular-automata-gpu/blob/master/README.md); [WebGLC claims up to 20x](https://github.com/ashtonsix/webglc/blob/master/./), vendor claim). Also, GPU float behaviour breaks the determinism requirement. Verdict: **overkill** for Clade; GPU is fine for the render/overlay only.
- **Dwarf Fortress** fluid rule: "Water falls down if it can, over if it can" and biomes come from temperature, rainfall, elevation, drainage fields ([Game Developer interview](https://gamedeveloper.com/design/interview-the-making-of-dwarf-fortress)). Layered scalar fields feeding derived state, same shape as Clade.

## 3. Explainability

- **Return breakdowns, not just values**: RimWorld's StatParts; CK3 added `GetScriptValueBreakdown` so UI shows "exactly the same data as if natively done from code" ([Dev Diary 87](https://www.paradoxinteractive.com/games/crusader-kings-iii/news/dev-diary-87-royal-modding)). Victoria 3 reuses CK3's nested tooltips ([PCGamesN](https://www.pcgamesn.com/victoria-3/nested-tooltip-system)) and states AI/sim transparency as a principle ([Dev Diary 59](https://paradoxinteractive.com/games/victoria-3/news/victoria-3-dev-diary-59-ai)).
- **Per-event debug**: CK3 event windows have icons to show raw keys, which trigger conditions passed, and scope info (Dev Diary 87 above). Equivalent for Clade: "why did this plant die/spread here?" showing which conditions passed.
- **Performance/debug views**: Factorio F4 debug settings: `show-time-usage`, `show-entity-time-usage`, `show-fps` ([Factorio wiki, Diagnosing performance](https://wiki.factorio.com/Tutorial:Diagnosing_performance_issues)). Per-system timing in a dev panel is cheap and catches the "one system ate the tick budget" case.
- **Overlays**: ONI and SimCity-style data overlays are standard; I did not find a primary source describing how they are built (**[not found]**). A layer overlay is a trivial typed-array to colour mapping.
- **Legibility vs depth** (Sylvester): players did not notice Ultima Online's predator-prey ecology; goal is a simulation "not overly complex, and that a player can observe and comprehend". RimWorld shows enough that "it constrains the imagination a little bit". Source: [Game Developer, RimWorld/DF formula](https://gamedeveloper.com/design/how-i-rimworld-i-fleshes-out-the-i-dwarf-fortress-i-formula). Also: "the richness comes when several events interact."
- **Replay/time travel**: seed + input log + periodic state hashes reproduce runs; capture RNG seed, input stream, and engine/content version ([bugnet replay QA notes](https://bugnet.io/blog/qa-testing-for-replay-recording-and-playback), [bug reporting with replays](https://bugnet.io/blog/bug-reporting-for-games-with-replays-and-spectating), blog-level sources). For a deterministic sim, "time travel" = keyframe snapshots every N ticks + re-sim forward.

## 4. Iteration and testing

What I found vs. not found: there is little published indie material on testing emergent sims (**[not found]** for headless/invariant testing in games; Tarn Adams' interviews do not discuss tests). Adams' tools are an arena mode to spawn units and watch ([PC Gamer](https://www.pcgamer.com/uk/dwarf-fortress-dev-log-remains-hilariously-grim)); his famous drunk-cat bug was "one number off in the ingest-while-cleaning code" ([Stack Overflow Blog](https://stackoverflow.blog/2021/12/31/700000-lines-of-code-20-years-and-one-developer-how-dwarf-fortress-is-built/)), i.e. in-game sandboxes plus noticing oddities, not automated tests. The rest below is adapted from ecology/ABM practice and general engineering.

- **Deterministic simulation testing**: the seed-replay idea comes from distributed-systems testing ([Phil Eaton's notes](https://notes.eatonphil.com/2024-08-20-deterministic-simulation-testing.html)): run many seeds headless, reproduce any failure by its seed.
- **Headless batch runner** (**[unverified]** as practice, but straightforward): the pure sim module runs in Node/Vitest with no DOM. A script runs S seeds × T ticks and prints a table.
- **Invariants**: no NaN/Infinity; every layer within its declared range; mass/nitrogen budget accounting (sources − sinks = delta); species IDs valid; no negative counts; same seed ⇒ same state hash.
- **Ecological metrics** (computed from per-species cell counts):
  - Richness (q=0), Shannon and Simpson as **Hill numbers** (effective species) — these put richness, Shannon and Simpson on one scale, and the q=0 vs q=2 gap measures dominance ([Hill-number docs, entropart](https://rdrr.io/cran/entropart/man/Diversity.html), [hilldiv](https://phylotastic.r-universe.dev/hilldiv/doc/manual.html)).
  - Temporal turnover (composition change between times; Jost's alpha/beta/gamma split) ([arXiv 1507.08484](https://arxiv.org/pdf/1507.08484)).
  - Coexistence time / persistence: ticks until first extinction, and fraction of species alive at T. No source found defining these for games (**[not found]**); they are trivial to compute from the same logs.
  - Targets should be **patterns, not exact numbers**: pattern-oriented modelling checks a model against several qualitative patterns at once, because a single pattern constrains structure poorly ([Grimm et al. 2005 via summary](https://courses.ecology.uga.edu/ecol8910-spring2017/2017/01/10/pattern-oriented-modeling-of-agent-based-complex-systems-lessons-from-ecology); caution about overfitting in [Topping et al. 2012](https://catalog.comses.net/publications/290)).
- **Sweeps and sensitivity**: Start with one-factor-at-a-time sweeps around the default; Sobol/Morris global methods exist for ABMs but need many runs and have limited information when interactions are nonlinear ([Thiele, Kurth & Grimm 2014](https://jasss.org/17/3/11.html), [Ligtenberg et al. 2016 via CoMSES](https://catalog.comses.net/publications/69689)). NetLogo's BehaviorSpace is the model for "run a grid of parameters, write a CSV". For a solo dev, OFAT + a plot is usually enough (my judgement).
- **Golden/snapshot tests**: hash the state at ticks 100/1000/10000 for 3-5 seeds. They detect unintended change, not correctness; update the hash deliberately when design changes. Useful mostly to prove fast-forward == live stepping and refactors preserved behaviour.
- **Hot-reload in Vite**: JSON imports are supported directly ([Vite features](https://vite.dev/guide/features.html)); `import.meta.hot.accept(deps, cb)` lets a module take updates ([Vite HMR API](https://vite.dev/guide/api-hmr)). Whether a JSON/TS data change hot-swaps without a reload depends on having an accepting boundary; I did not verify this and it needs a 10-line test. Simplest robust loop: data change ⇒ rebuild the world from the same seed and fast-forward to the same tick (needs determinism).
- **In-game sandbox**: Adams' arena mode; CK3's `bypass`/`save_every` console commands (Dev Diary 87). A "paint layer values / place species / step N ticks / reseed" panel is the Clade equivalent of both.

## 5. Determinism and fast-forward in JS

- **Rune's lockstep findings** ([Rune blog](https://developers.rune.ai/blog/making-js-deterministic-for-fun-and-glory/)): many `Math` functions have implementation-dependent precision (they rounded results of ~30 functions with `Math.fround`); `Math.random` cannot be seeded (use e.g. mulberry32); `Array.prototype.sort` differs between engines, especially on strings and malformed comparators; they ship an ESLint plugin for nondeterministic patterns. They did not cover `Date`, `Map` iteration order, or patch costs.
- **Rapier docs** also warn that transcendental functions (`sin`, `cos`) are not cross-platform deterministic ([Rapier determinism](https://rapier.rs/docs/user_guides/javascript/determinism)). IEEE 754 fixes `+ - * /` and `sqrt` bit-exactly ([alice-det-math docs](https://docs.rs/alice-det-math), a Rust crate; the JS-engine behaviour of the four basic ops I take as correct but did not verify per engine).
- **My reasoning [unverified]**: for a single-player game, cross-engine determinism only matters for (a) sharing seeds or saves across browsers, (b) running golden tests in Node (V8) and shipping to Firefox/Safari. Same-engine determinism (same seed ⇒ same result) is what fast-forward needs. Simplest rules: only `+ - * /`, `Math.sqrt`, `Math.fround`, `Math.floor`, integers; precompute lookup tables for `exp`/`pow`/curves at startup using exact arithmetic; seeded PRNG with one stream per system (derive by hashing name, as Rune does) so adding a system does not shift others' draws.
- **Fixed-point/integers**: Int32 or Uint16 quantities (e.g. nitrogen in 1/256 units) remove float worries entirely and make hashing and diffing exact. Cost: awkward rate math. Consider for stocks (layers), keep floats for derived factors, rounding on write.
- **Offline progress approaches seen in idle games**: full tick simulation ("every single tick", Melvor community claim), lighter "record rate on exit, multiply by elapsed time" (Clicker Heroes), average income over a window times elapsed, flat fraction of production; devs say simulating hours in seconds is acceptable and that you should decouple logic from rendering so logic can run in bulk. Sources: [Clicker Heroes blog](https://blog.clickerheroes.com/offline-progression-in-clicker-heroes/embed/), [itch.io forum thread](https://itch.io/post/14654594), [Melvor discussion](https://steamcommunity.com/app/1267910/discussions/0/591762563949134719), [Four Divine Abidings devlog](https://fourda.itch.io/four-divine-abidings/devlog/861740/update-03012025). All anecdotal/forum-grade.
- **Web Workers**: no devlog found (**[not found]**). Practical note **[unverified]**: run the sim in a worker, batch-step in slices (e.g. a few thousand ticks per message) with progress events; layers as typed arrays can be transferred or shared (`SharedArrayBuffer` requires cross-origin isolation headers; bitECS documents SAB-backed typed arrays for workers: [Multithreading doc](https://cdn.jsdelivr.net/npm/bitecs@0.4.0/docs/Multithreading.md)).
- **Analytical catch-up** is only valid for the parts with closed forms (e.g. exponential decay of a layer toward equilibrium). Species competition on a grid is path-dependent; fast-forward by real stepping, with an optional cap and "coarse mode" (skip rendering, slower layers at multiples) when the elapsed time is huge.

## Use in Clade (all **proposals**)

### Recommended lean setup, in build order

1. **Species as data, effects from a fixed vocabulary.** A `SpeciesDef` is: id, tags[], numeric traits, and a short list of effect entries chosen from ~8-12 effect kinds implemented once (e.g. `consumes(layer, rate)`, `emits(layer, rate)`, `needs(layer, min, max, curve)`, `shades(strength)`, `fixes(nitrogen)`, `eaten_by_tag`). Keep it in typed TS files (`defineSpecies({...})`) so the compiler checks field names; add a startup `validate()` that checks ranges, referenced layers/tags exist, and warns on unknown keys (Factorio ignores unknown keys silently; do the opposite).
2. **Interactions go through layers and tags, never species pairs.** Add a pair override table only when a real exception appears; log each use.
3. **One definition per layer**: `LayerDef {id, type, range, combine: 'sum'|'max'|'mul', diffuses, period, doubleBuffered}`. Combine rule and clamp live here, not in species.
4. **Systems list**: a single ordered array of `{name, period, phase, fn}`; per-system timing counters exposed to the dev panel. No ECS library; typed arrays per layer, `speciesId`/`age` arrays for occupancy.
5. **Explain path from day one**: the growth/death/spread functions take an optional `trace` collector (null in production) and push `{factor, value}` pairs; the tile inspector shows them. Plus a ring-buffer event log with cause codes (`DIED:drought`, `OUTCOMPETED:shade`).
6. **Headless harness** (Vitest + a `npm run sim -- --seeds 20 --ticks 20000` script): invariants, Hill numbers q=0/1/2, extinction count and times, turnover, wall-clock per tick; prints a table and writes CSV. Plus 3 seed golden hashes.
7. **Determinism rules** written in `docs/` and enforced by an ESLint `no-restricted-properties` for `Math.random`, `Date.now`, `Math.sin/cos/exp/pow` in `src/sim/`. One PRNG stream per system.
8. **Fast-forward** = the same `step()` in a time-sliced loop (worker later), tested by "live N ticks == FF N ticks" hash equality.
9. **Dev panel** extras after the above: layer overlays, paint/place tools, reseed + rebuild-and-fast-forward on data change (the simplest hot reload).

### Overkill for a solo dev now

- GPU/WebGL/WebGPU simulation; multithreaded chunking (Noita); dirty rects.
- A general ECS library; a custom DSL/scripting language for effects (typed TS data suffices).
- Full Sobol/Morris sensitivity analysis; a balance bot (project rule already says no).
- Fixed-point everywhere; analytical catch-up for the whole ecosystem.
- Mod/patch layering (Factorio's three data rounds, XML patching) unless modding is a goal.

### Five pitfalls

1. **Pair-wise creep**: "just one special case for A vs B" repeated 100 times gives the N×M table back. Gate with tags/channels; make every pair override logged and counted.
2. **Float and engine nondeterminism sneaking in** (`Math.pow/exp/sin`, `Math.random`, string sort, iteration over object keys) breaks fast-forward==live and golden tests; fix cost grows with code size. Lint it early.
3. **Un-explainable outcomes** at 100+ species: if you cannot see why a species died, you tune blind and the player sees noise (Sylvester: players did not perceive Ultima Online's ecology). Build the trace before more species.
4. **Tuning with eyes only, on one seed**: a change that looks good on the seed you stare at can collapse diversity on others. Always compare metrics over a seed set, and watch for overfitting to the pattern you chose (Topping et al. caution).
5. **Optimising or architecting for scale you do not have** (GPU, ECS, workers) while the real cost is content/iteration speed; conversely, ignoring per-system timing until offline fast-forward of many hours is too slow. Measure ticks/second headless first and set a budget (e.g. 8 h offline within a few seconds, cf. Four Divine Abidings' "up to 24h in several seconds").
